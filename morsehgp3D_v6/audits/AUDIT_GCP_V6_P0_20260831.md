## Verdict courant

**NO-GO maintenu pour toute session facturable, y compris `smoke_v1`.**

Ce NO-GO ne vient plus d'un P0 de fermeture de VM. Le chemin nominal possède
désormais un point d'entrée externe exécutable et une composition crédible du
vrai garde avec le cleanup extérieur ; un arrêt extérieur réussi publie bien
`targeted_stopped`. Les deux défauts de sûreté du premier tour sont reçus.

La dépense reste prématurée parce que quatre défauts locaux peuvent rendre le
reçu non rejouable ou promouvoir une matrice réduite en
`decision_complete`. Ils sont courts à corriger sans VM. Une fois ces portes
causales vertes, un nouvel audit devrait pouvoir statuer sans quatrième
refonte du cycle de vie.

## Reçu — sûreté de démarrage et d'arrêt

Le troisième tour ferme matériellement les points suivants :

- l'entrée documentée depuis `/tmp` reçoit une racine explicite, canonique et
  validée, résout un commit complet et utilise `git -C` ; le selftest traverse
  réellement cette entrée hors dépôt jusqu'au pin ;
- l'appel simple de l'étage 2 avec le script du worktree et un `WORK` vide est
  refusé ; bootstrap et pin exécutés sont recoupés avec les blobs du commit ;
- la création initiale du registre utilise `O_EXCL` ;
- le cleanup extérieur publie `targeted_stopping`, puis
  `targeted_stopped` ou `targeted_stop_failed`, et retente explicitement une
  fois après un échec d'arrêt interne ;
- l'intégration compose le vrai `start_and_verify.sh`, le vrai cycle de vie,
  un faux `gcloud` et un faux stop compteur : elle obtient un arrêt unique à
  la génération exacte et un reçu `stop_rc=0` / `targeted_stopped` ;
- `CLOUDSDK_CONFIG` est copié dans le répertoire privé, les axes de profil
  supplémentaires sont gravés, et les sorties distantes ont un manifeste.

Deux surclaims doivent néanmoins disparaître. Un appelant peut préparer un
`WORK` arbitraire contenant les deux blobs exacts, placer le marqueur d'étage
2 puis exécuter `WORK/bootstrap.sh` : l'étage 2 est atteint sans handoff de
l'étage 1. Cela ne permet pas d'exécuter du code non épinglé et ne constitue
donc pas un P0 dans le modèle opérateur honnête ; écrire « handoff prouvé » ou
« étage 2 non forgeable » est toutefois faux. Le mutant actuel, qui invoque
le script du worktree avec un `WORK` vide, est trop faible.

De même, l'ancien registre extérieur périmé n'était pas un P0 de facturation :
le retour zéro de `stop_and_verify.sh` certifiait déjà l'arrêt de la cible
exacte. C'était un P1 de cohérence et de reçu, maintenant corrigé sur le
chemin nominal.

## P1 bloquant — le profil canonique n'est pas l'autorité des axes

`validate_v6_campaign.py` vérifie que le hash transporté correspond au
fichier canonique fourni, mais ne parse jamais ce fichier et ne compare aucun
de ses axes au profil effectif. Le statut final ne teste que :

```text
profil == profil_canonique == decision_v1
```

Un profil réduit peut donc porter les deux noms `decision_v1`, le vrai hash
du canon, puis des plans réduits concordants et recevoir
`decision_complete`. En outre, `run_timeout`, `v5_gate_min` et
`v6_gate_min` sont écrits mais pas exigés par le validateur.

Correction minimale : parser le canon avec une grammaire fermée, exiger une
occurrence unique de chaque axe, comparer littéralement tous les axes
effectifs au canon et réserver `decision_complete` à cette égalité exacte.
Ajouter un mutant à matrice réduite qui doit être **valide non décisionnel**
ou refusé pour cette cause précise.

## P1 bloquant — le selftest tue plusieurs mutants par une cause parasite

Le premier passage du validateur contrôle `MANIFESTE_DISTANT.txt`, puis écrit
`bench_resume.txt` et `queue_resume.txt` dans le même `out/`. Ces deux fichiers
n'existaient pas dans le manifeste distant. Tout second passage sur ce dossier
échoue donc génériquement sur l'inventaire.

Le selftest réutilise précisément cet `out/` déjà enrichi pour les cas
`remote_rc`, `scp_rc`, profil réduit, hash canonique et prétention
`decision_v1`. Le dernier cas n'exige même pas un code zéro ; il vérifie
seulement l'absence de la chaîne `decision_complete`. Les verts annoncés ne
démontrent donc pas leurs causes.

Correction minimale : ne jamais écrire les résumés locaux dans l'inventaire
distant, ou valider un snapshot brut immuable et publier les résumés à côté.
Chaque mutant doit repartir de ce snapshot propre, exiger le code et le
diagnostic exacts, et le validateur doit être idempotent.

## P1 bloquant — le reçu publié possède un manifeste mécaniquement faux

Dans `finalize_receipt`, le shell ouvre `SHA256SUMS.tmp` avant d'exécuter
`find`. Le filtre exclut seulement `SHA256SUMS`, donc inclut le temporaire en
cours d'écriture. Après son renommage, `sha256sum -c SHA256SUMS` cherche
`SHA256SUMS.tmp`, désormais absent, et rend 1.

La publication reste en outre sujette à deux courses : test d'absence suivi
de `mkdir -p <dir>.partial`, puis `mv` sans garantie no-clobber si la cible
apparaît. Enfin, trois messages d'échec référencent encore
`DURABLE_RECEIPT_DIR`, variable supprimée ; sous `set -u`, un échec de reçu
dérive vers `unbound variable` au lieu du code 66 documenté.

Correction minimale : créer un temporaire réellement unique par `mktemp -d`
dans la base, produire le manifeste vers un fichier extérieur ou exclure
`SHA256SUMS*`, vérifier immédiatement `sha256sum -c`, puis publier avec une
primitive no-clobber. Utiliser partout `DURABLE_RECEIPT_BASE` et graver les
trois chemins d'échec dans le selftest.

## P1 — registre et preuve de pin à durcir

- L'écriture initiale `O_EXCL` est exclusive, mais directe dans le nom final :
  une interruption peut laisser un enregistrement partiel. Combiner un verrou
  exclusif avec une publication temporaire + `fsync` + renommage, ou employer
  un lien dur exclusif depuis un temporaire fsyncé.
- `state_field` reste un `sed | head` permissif. Il ne vérifie ni schéma, ni
  unicité, ni document complet. Le fast-path `targeted_stopped` ne compare pas
  explicitement la génération du registre à la génération verrouillée.
- Bootstrap et pin sont hashés puis relus par Bash. Dans le répertoire 0700
  produit par l'étage 1, le risque est borné ; le claim d'un handoff
  cryptographique exigerait toutefois de supprimer cette fenêtre de relire.
- La nouvelle fixture K11 contient deux fois `digest_forest_K1`. Le chargeur
  rend donc déjà 2 sur le doublon ; la porte ne prouve pas causalement le
  refus de K11. Supprimer le doublon et, idéalement, distinguer le diagnostic.

Ces points n'impliquent pas qu'une VM serait oubliée sur le chemin nominal.
Ils empêchent de prétendre que le journal, le profil et les portes sont
transactionnels et causaux de bout en bout.
