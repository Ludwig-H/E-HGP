## P0 — état illisible pris pour état absent

`state_snapshot()` capture tout `OSError` et retourne 3, code documenté pour
un fichier absent. Le probe exécutant la fonction exacte de `e018b4c8`
donne :

```text
chemin absent                         -> rc=3
/tmp (répertoire, IsADirectoryError)  -> rc=3
/etc/hostname (contenu hors schéma)   -> rc=4
```

Injecté dans le cleanup exact, le cas répertoire sans handoff publie
`issue=refus_avant_mutation` au lieu de bloquer avec 71. Une erreur d'accès,
d'E/S ou un chemin non régulier peut donc certifier à tort qu'aucun start
n'a été demandé.

Correction minimale : seul `FileNotFoundError` vaut « absent » ; tout autre
`OSError`, `UnicodeError`, lien ou type non régulier vaut « illisible ». Le
mutant doit exiger blocage 71, commande de contrôle et zéro assertion
« avant mutation ».

## P0 — une génération d'une autre cible autorise le stop

Sans handoff ni génération en mémoire, le cleanup adopte `lc_gen` d'un
snapshot strict sans exiger que `lc_project/lc_zone/lc_instance` désignent la
cible configurée. Le probe exact fournit un registre
`autre-projet/autre-zone/autre-instance` puis observe :

```text
generation adoptee du registre STRICT : 2026-08-31T14:00:00Z
STOP --yes --expected-last-start-timestamp 2026-08-31T14:00:00Z
```

L'appel vise pourtant la cible d'environnement factice, pas celle du
registre. `stop_and_verify.sh` refuse normalement une génération différente,
mais une valeur concordante suffit à contourner l'autorité de cible.

Exiger la cible exacte avant toute adoption. Cible discordante sans handoff
exact : blocage et contrôle manuel, jamais appel mutateur.

Le fast-path fondé sur le seul registre a aussi un défaut de preuve : avec
`targeted_stopped` à `2026-08-31T14:00:00Z`, le reçu observé contient
`generation=inconnue` et `run_id=s_avorte_*`. Affecter puis valider
`GENERATION` et `GEN_EPOCH` avant de finaliser ce reçu. Après un stop
extérieur, reparser un snapshot strict au lieu de décider avec
`state_field`.

## P0 — les délais ne tuent pas les processus récalcitrants

`run_one`, les SSH de build/campagne et les SCP appellent GNU `timeout` sans
`--kill-after`. Un processus qui ignore `TERM` peut donc dépasser la borne et
empêcher le trap d'arrêt d'être atteint. Probe local borné : un timeout
interne de 0,1 s autour d'un processus ignorant `TERM` ne termine qu'au
SIGKILL de l'enveloppe extérieure, après 1,204 s, code 137.

La marge de rapatriement n'est pas cohérente avec les enveloppes :

- deadline des runs : T+455 min (`28800 - 1500` s) ;
- enveloppe SSH de campagne : jusqu'à T+460 min par le `+300` ;
- coupe-circuit invité : environ T+470 min ;
- un SCP : 30 min, jusqu'à trois tentatives, plus les attentes.

Ainsi, même un seul SCP ne tient pas dans les dix minutes restantes au pire
cas. Le coupe-circuit GCE reste un dernier filet à T+480 min, mais il ne
remplace ni l'arrêt ciblé immédiat ni un rapatriement borné.

Ajouter un `--kill-after` court à chaque timeout, y compris aux enveloppes
SSH/SCP. Calculer chaque durée sur le temps réellement restant jusqu'au plus
proche des deux coupe-circuits, supprimer le dépassement `+300`, et réserver
avant mutation une marge couvrant la politique de retry annoncée.

## Frontière encore fail-open

Les probes sont causaux : après chaque mutation, `MANIFESTE_DISTANT.txt` a
été entièrement recalculé avant de relancer le validateur sur le snapshot
nominal de 83 fichiers (`ec68435d...c2ed9`).

| Mutation de la frontière | Verdict observé |
|---|---|
| `code=abc` avec `bad_alloc` | accepté, rc 0 |
| `code=3` avec `bad_alloc` | accepté, rc 0 |
| `code=9`, `bad_alloc` et une ligne `INVARIANT` | accepté, rc 0 |
| `code=0` avec une ligne `INVARIANT` | accepté, rc 0 |
| `duree_s=abc` | accepté, rc 0 |
| argument décoré `xxx--n=400000xxx` | accepté, rc 0 |
| `code=124` avec une ligne `INVARIANT` | accepté, rc 0 |
| commande sans `ulimit`, plan à `183500800` kB | accepté, rc 0 |

Cela réfute « trois classes et rien d'autre ». Le code et la durée non
numériques ne sont pas rejetés ; tout non-zéro accompagné du mot `bad_alloc`
passe ; le succès et le timeout contournent les motifs fatals ; les arguments
sont cherchés par sous-chaîne. Le plafond est lié profil→plan, mais pas
plan→commande exécutée.

Classifier explicitement : succès 0 avec contrat complet et motifs interdits
scannés ; timeout attesté par le superviseur ; code 2 uniquement avec le
message exact `REFUS resource_exhausted` du pipeline ; éventuel abort 134
avec diagnostic exact `std::bad_alloc` et `RLIMIT_AS` attesté. Codes 3, 127,
139, code absent/non numérique et signaux non attribués invalident la phase.
Graver `limit_kind=rlimit_as` et `limit_kb` dans chaque statut et le résumé,
puis recouper la commande.

Même corrigée, cette mesure sera une frontière **sous plafond virtuel
RLIMIT_AS**, pas le mur RAM natif de la VM : l'espace d'adressage inclut des
mappings non résidents.

## Mutants, budget et ordre de mesure

Le selftest officiel est vert, mais `falsify()` modifie un artefact sans
réécrire le manifeste distant et n'exige que rc 1. Ses nouveaux mutants GPU,
fils et frontière peuvent donc mourir sur le hash avant la porte sémantique.
Les probes réhashés confirment indépendamment le refus GPU index sans
`--gpu-wire=index` et la non-vacuité fils ; ils réfutent la frontière. Faire
du réhash une option explicite du helper et exiger le diagnostic causal.

Le mutant « publication interrompue » fabrique seulement un `.partial` dans
le faux garde ; il n'interrompt pas le vrai `os.link`. La publication finale
est bien atomique, mais une erreur d'écriture, fsync ou lien autre que
`FileExistsError` laisse le temporaire. Un `sitecustomize.py` local qui fait
lever `EIO` à `os.link` permet de tester le vrai chemin : aucun start, aucun
fichier final et aucun `.partial` doivent subsister.

Le reçu est atomiquement cohérent après exécution, mais sa publication ne
fsync ni tous les fichiers, ni le répertoire temporaire, ni le parent final.
Employer ce libellé borné ou ajouter ces barrières avant de revendiquer une
durabilité après crash.

Le budget dit « conservateur » estime le GPU G4 à 3 940 s alors que ses
timeouts permettent 48 000 s, et la frontière à 6 700 s contre 14 400 s.
Le garde par run peut tronquer la campagne, mais le preflight ne garantit pas
que le profil annoncé finira. Renommer ces valeurs en estimation nominale et
publier séparément l'enveloppe de terminaison.

Enfin, le build CUDA v5 précède encore queue et bench : il peut contaminer
les mesures CPU. Ordre utile : différentiel, fils/queue/bench CPU, GPU
historique, puis frontière. Les commentaires de `g4_mesure_v1` doivent aussi
abandonner « bit-identité » et « gain GPU » : les portes prouvent un
grand-livre invariant et des observations historiques, pas ces claims.

## Contre-audit des objections secondaires

Je ne retiens pas comme P0 le manifeste réduit accepté par le validateur
appelé isolément : dans le chemin réel, le lanceur reconstruit l'ensemble
normatif `PROTOCOL_FILES` et vérifie son hash avant mutation. De même, un
`PROFIL_NOM` vide ne peut pas produire `decision_complete` et aucun canon
livré n'est vide. Ces grammaires devraient échouer fermement, mais elles ne
sont pas la raison du présent NO-GO.
