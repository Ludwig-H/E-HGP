# Audit de suivi — protocole GCP v6, vérification de `e018b4c8`

Date : 2026-08-31.

Autorité inspectée : `e018b4c8` (`porte gcp cinquieme tour : les six points
executes`). Revue statique, faux pilotes et tests locaux seulement ; aucune
ressource GCP n'a été créée, démarrée, arrêtée ou modifiée par cet audit.

Cadre v6 :

- `phase=exploration_v6_hors_registre`
- `backend=cpu_reference`
- `profile=quantized_u16_input_only`
- `mode=audit_independant_math_and_architecture`
- `public_status=not_claimed`

## Verdict courant

**NO-GO maintenu pour toute session facturable, y compris
`g4_mesure_v1`.** La réponse ferme une grande majorité des défauts du tour
précédent et mérite d'être conservée. Deux contre-exemples fail-closed restent
toutefois actifs : un registre présent mais illisible peut encore être traité
comme absent, et six pannes de frontière falsifiées obtiennent encore le code
0 du validateur quand le manifeste de transport est recalculé.

Le correctif demandé est désormais petit et ciblé. Il n'est pas nécessaire de
reconcevoir le protocole ni de refaire les campagnes CPU.

## Fermetures reçues

Le profil G4 exact passe désormais le runner puis le validateur avec 81 runs :
16 accords différentiels, 34 runs de fils, 19 contrôles GPU historiques, 8
runs de bench, 4 runs de frontière et une queue vide. Le désaccord 81/82 lié à
`aucun` est fermé.

La génération exacte participe maintenant au fast-path d'arrêt ; registre
perdu ou corrompu avec handoff valide conduit à l'arrêt ; la reprise réalise
effectivement deux appels ordonnés ; la première publication du registre est
exclusive, atomiquement observable et fsyncée sur son chemin nominal. Les six
mutants de cycle ajoutés sont utiles.

La liaison canon–manifeste ferme l'exploit coordonné : nom, hash, taille,
chemin et commit sont recoupés. Les grammaires du canon et du manifeste
distant sont fermées, les cinq résumés entrent dans le reçu, la frontière est
exécutée en dernier, et la phase CUDA est correctement bornée comme contrôle
v5 historique non autoritaire. La porte de fils juge désormais honnêtement
l'invariance du grand-livre avec non-vacuité, pas l'identité de l'objet.

## P0 — une erreur de lecture du registre devient une fausse absence

Dans `state_snapshot()`, tout `OSError` produit le code 3. Le cleanup interprète
ensuite ce code comme « registre absent » et, sans handoff ni génération en
mémoire, conclut `refus_avant_mutation` sans arrêt ni blocage. Or
`PermissionError`, `EIO`, `IsADirectoryError` ou un lien symbolique pendant ne
prouvent pas l'absence du registre ni l'absence d'un démarrage antérieur.

Correction minimale : seul `FileNotFoundError` doit signifier absent ; tout
autre défaut de lecture, objet non régulier ou lien symbolique doit signifier
illisible et conduire au blocage 71 en l'absence d'une génération indépendante.
Ajouter un mutant post-mutation sans handoff où le chemin du registre existe
mais est illisible et exiger le blocage, jamais `refus_avant_mutation`.

Le parseur dit aussi être strict sans imposer d'alphabet à `project`, `zone`,
`instance` et `generation`, alors que son résultat est transporté par des mots
séparés puis relu par `read`. Fermer ces alphabets et partager la même règle
avec le handoff évitera qu'espaces, tabulations ou retours chariot décalent le
tuple. Ce second point est une fermeture de preuve ; la garde d'arrêt exacte
limite déjà sa portée opérationnelle.

## P0 — six faux succès de frontière

Le probe indépendant part du nominal du selftest, applique une mutation
isolée, **recalcule ensuite `MANIFESTE_DISTANT.txt`**, puis invoque le
validateur avec les mêmes pins, profil, canon et manifeste revalidé. Les six
cas suivants rendent tous `rc=0` :

| Mutation isolée | Résultat observé |
|---|---:|
| `code=abc` avec un corps contenant `bad_alloc` | 0 |
| ajout de `INVARIANT` au refus `bad_alloc`, code 9 | 0 |
| ajout de `INVARIANT` à un pipeline complet, code 0 | 0 |
| `duree_s=abc` | 0 |
| argument décoré `xxx--n=400000xxx` | 0 |
| code 124 avec `INVARIANT` | 0 |

Les causes sont localisées : l'absence de correspondance numérique pour
`code` devient seulement `?` ; `code_free=True` désactive `FORBIDDEN` pour
toutes les classes de frontière ; une durée non numérique devient `None` sans
faute ; les arguments sont cherchés comme sous-chaînes dans `commande`.

Correction constructive : exiger un code décimal unique et une durée décimale,
analyser les arguments comme tokens exacts, et appliquer à toutes les classes
un motif fatal qui rejette au minimum invariant, divergence, plancher,
sanitizer et panne d'infrastructure. Le refus de capacité peut autoriser
`bad_alloc`/`resource_exhausted`, mais pas les masquer s'ils coexistent avec un
motif fatal. Le code 124 doit être décrit prudemment comme timeout observé par
l'enveloppe, ou être distingué d'un binaire qui sortirait lui-même 124.

## Les mutants actuels ne sont pas causaux

`falsify()` modifie un artefact copié mais ne régénère jamais
`MANIFESTE_DISTANT.txt`. Le validateur refuse donc déjà la copie au contrôle du
hash de transport. Cela ne prouve pas que la porte sémantique annoncée a tué le
mutant ; le faux succès ci-dessus apparaît précisément lorsque cette cause
étrangère est retirée.

Ajouter deux helpers distincts : corruption de transport sans rehash, et
mutant sémantique avec rehash puis diagnostic exact. Les mutants code, durée,
motif fatal et argv doivent emprunter le second chemin. Cette discipline doit
aussi être appliquée aux tests GPU, fils, compteurs et plans qui revendiquent
actuellement une cause sémantique.

## Budget et durées — portée à corriger avant de payer

L'ordre réel des phases est bon et les coupe-circuits restent bornés. En
revanche, le préflight se nomme « conservateur » alors que G4 estime 22 984 s
dans une fenêtre de 26 400 s en créditant seulement 1 860 s aux deux builds
GPU. Leurs deux plafonds canoniques valent chacun 3 600 s ; cette substitution
seule porte le total à 28 324 s. Le préflight est donc une prévision empirique,
pas une garantie que les 81 runs terminent.

De même, les deux gardes de build réservent exactement 3 600 s, sans marge de
publication du statut. La deadline de campagne tombe vers 455 minutes,
l'enveloppe distante peut aller environ 300 s plus loin, et l'arrêt invité est
armé à 470 minutes, alors qu'une tentative SCP peut durer 1 800 s. La marge de
rapatriement annoncée n'est pas garantie par ces délais imbriqués.

Deux choix honnêtes sont possibles : réduire la matrice ou les plafonds pour
obtenir une borne ; ou qualifier G4 de campagne exploratoire tronquable et le
budget de prévision empirique. Dans les deux cas, réserver un petit overhead
par run et aligner deadline, timeout externe, arrêt invité et timeout SCP.
`FRONTIER_ULIMIT_KB` borne en outre l'espace virtuel, pas le RSS, et favorise
un `bad_alloc` sans le garantir.

## Contrôles indépendants à `e018b4c8`

- syntaxe Bash, compilation Python, `git show --check` : succès ;
- `selftest_campagne_v6.sh` : succès, profil G4 exact compris ;
- `selftest_cycle_vie_v6.sh` : succès, 21 scénarios et 11 refus de pin ;
- `tests.gcp.test_gcp_safety` et `test_v6_lifecycle_integration` : 82/82 en
  121,048 s ;
- six mutants de frontière avec rehash causal : **6/6 acceptés à tort**.

Le reçu est atomiquement publié et cohérent par SHA après le processus. Il ne
possède toutefois pas les `fsync` des fichiers, des répertoires temporaires et
du parent final nécessaires pour revendiquer une durabilité après crash. Soit
ajouter cette persistance, soit employer le libellé plus exact
« atomique et cohérent après exécution ».

## Porte de réouverture minimale

1. distinguer absence et illisibilité du registre, avec mutant causal ;
2. fermer code, durée, motifs fatals et argv de frontière ;
3. recalculer le manifeste dans chaque mutant sémantique et exiger sa cause ;
4. aligner ou borner les claims de budget, deadline et durabilité ;
5. rejouer les portes locales et demander le verdict frais sur le nouveau pin.

GCP non utilisé par le présent audit.
