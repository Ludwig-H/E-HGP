15: ## Demande de l'utilisateur (2 octobre 2026)
16: 
17: « Repartir de zéro pour avoir quelque chose de plus propre. Mêmes contrats : 100 ms sur nuages LiDAR sans sol
18: (éventuellement avec sol), avec K = 5 et si possible K = 10. Toujours très rigoureux mathématiquement. Il faut ensuite
19: se comparer à HDBSCAN, sur données synthétiques mais aussi sur données réelles. Il y a notamment des tests dans le
20: dossier `Zoltan/` où la hiérarchie HDBSCAN échoue ; on peut en trouver d'autres. Il faudrait des exemples où la
21: hiérarchie HGP réussit. » Puis : commencer sans attendre la fin de l'audit de la v10, en reprenant les bases très
22: solides.
23: 
24: ## Objet
25: 
26: Pour $k = 1, \ldots, K_{\max}$ et $a \geq 0$, soit $D_k(y)$ le carré de la distance de $y$ à son $k$-ième plus proche point et $L_k(a) = \lbrace y \in \mathbb{R}^{3} : D_k(y) \leq a \rbrace$. La **tour FULL** est, pour chaque $k$, l'arbre de fusion des composantes connexes de $L_k(a)$ quand $a$ croît, avec les applications verticales $L_{k+1}(a) \subseteq L_k(a)$ ; les niveaux sont des rationnels exacts. La v11 calcule ensuite une hiérarchie laminaire sur les points, à comparer à celle de `sklearn.cluster.HDBSCAN` (jamais réimplémenté).

1: # Architecture de la v11
2: 
3: Document normatif pour le code de `morsehgp3D_v11/`. Il fixe ce que « propre » veut dire ici, la carte des modules,
4: le profil numérique et les conventions de construction et de test. Les énoncés mathématiques vivent dans
5: `MATHEMATIQUES.md` (à venir avec le moteur) ; ce document n'en recopie aucun.
6: 
7: ## 1. Règles de propreté
8: 
9: Chaque règle est vérifiable ; `tools/check_style.py` contrôle celles qui se lisent dans le texte du code.
10: 
11: 1. **Un module = un dossier = un en-tête public** `src/<module>/<module>.hpp`. Les autres fichiers du dossier sont
12:    internes. Un module ne dépend que des modules placés avant lui dans la table du § 2 ; aucun cycle.
13: 2. **Taille** : un fichier de `src/` fait au plus 500 lignes, une fonction au plus 100. Un fichier qui approche la
14:    limite se découpe par responsabilité, jamais par numérotation (`part1`, `part2`).
15: 3. **Aucun état global modifiable.** Une `Session` porte l'unique `MemoryBudget` et l'unique `Pool` ; ils sont
16:    passés explicitement.
17: 4. **Erreurs** : `Outcome` et `Result<T>` ; aucune exception ne traverse une frontière de module ; jamais `assert`
18:    (une précondition interne violée rend `invariant_violated`).
19: 5. **Transactions** : une opération rend son résultat entier ou un refus ; jamais un préfixe publié.
20: 6. **Aucun mutant, crochet de test ni option morte dans le produit.** Les mutants sont des correctifs appliqués à une
21:    copie des sources (`tests/mutants/`). Une option n'existe que si une porte l'exerce et qu'une ablation la justifie.
22: 7. **Déterminisme** : toute sortie publiée est identique octet pour octet quel que soit le nombre de fils. Une tâche
23:    parallèle écrit à des positions fixées par son ordinal ; les concaténations passent par des préfixes.
24: 8. **Mémoire** : tout grand tableau est un `Buffer<T>` réservé dans le budget avant l'allocation. `std::vector` est
25:    permis pour les petits états locaux hors boucle chaude.
26: 9. **Chaque décision est entière et exacte.** Le flottant suit la doctrine du § 4.
27: 10. **Chaque prédicat cite son budget de bits** (§ 3) et le garde par `static_assert` ; chaque élagage cite son lemme.
28: 11. **Style** : C++20 sans extension (hors `__int128`, déclaré par `__extension__`), deux espaces, `snake_case` pour
29:     fonctions et variables, `PascalCase` pour les types, namespace `mhgp11`, macros `MHGP11_*`, cibles et tests
30:     `mhgp11_*`. Commentaires en français sans accents. Compilation `-Wall -Wextra -Wpedantic -Werror`, GCC et Clang.
31:     Python : PEP 8, aucune porte ne repose sur `assert`.

55: ## 3. Profil numérique
56: 
57: - Entrée : coordonnées entières $0 \leq x < 2^{B}$ par axe. $B$ = `MHGP11_COORD_BITS`, constante de compilation,
58:   **18 par défaut** (grille de 1 mm sur une trame LiDAR). Les profils $B = 21$ et $B = 24$ doivent compiler depuis les
59:   mêmes sources ; seul $B = 18$ est qualifié tant qu'un profil n'a pas ses propres portes.
60: - Les identifiants de points sont des `u32` arbitraires et uniques ; les positions égales forment un site de
61:   multiplicité $w \geq 1$.
62: - **Entiers à budget** : `num::Int<bits>` désigne le plus petit type exact capable de porter tout entier de valeur
63:   absolue $< 2^{\text{bits}}$ (`i64`, `i128`, puis entiers larges à mots de 64 bits). Le budget de chaque expression
64:   est calculé en `constexpr` à partir de $B$ ; aucun type n'est choisi à la main. Un débordement est donc une erreur
65:   de compilation, pas une garde à l'exécution.
66: - Les différences de coordonnées sont de valeur absolue $< 2^{B}$ (et non $2^{B+1}$).
67: - Un niveau est un rationnel exact `num / den`, `den > 0`, jamais réduit ; l'ordre des niveaux se décide par produits
68:   croisés exacts.
69: 
70: ## 4. Doctrine flottante
71: 
72: La v10 a dû refuser une à une les options de compilation qui affaiblissent IEEE-754 (raccord R2, constat B2), sans
73: pouvoir fermer tous les canaux. La v11 ne s'appuie pas sur un contrat de compilation : ses usages du flottant restent
74: justes sous tout mode d'arrondi, avec ou sans contraction, avec ou sans réassociation.
75: 
76: - **F1.** Aucune décision n'est prise en flottant.
77: - **F2.** Noyaux entiers portés en binaire64 : toutes les valeurs, y compris toute somme partielle dans un ordre
78:   quelconque, sont des entiers de valeur absolue $< 2^{53}$. Le calcul est alors exact, quel que soit le mode.
79: - **F3.** Clés approchées : obtenues à partir d'entiers exacts par conversions, produits, quotients et sommes de
80:   termes de même signe seulement. Sous la seule hypothèse qu'une opération élémentaire a une erreur relative
81:   $\leq 2^{-52}$, une clé issue de $m$ opérations a une erreur relative $\leq (1 + 2^{-52})^{m} - 1$. Aucune
82:   soustraction entre approximations.
83: - **F4.** Deux clés approchées ne sont déclarées ordonnées que si leur écart dépasse la marge prouvée ; sinon la
84:   comparaison est rejouée en exact.
85: - **F5.** Défense en profondeur, sans rôle dans les preuves : refus de `__FAST_MATH__` à la compilation, et auto-test
86:   des hypothèses F2 et F3 au démarrage d'une `Session`.
87: 
88: ## 5. Construction et portes
89: 
90: - `CMakeLists.txt` inclut `src/<module>/module.cmake` (sources de la bibliothèque `mhgp11`) et
91:   `tests/<module>/tests.cmake` (portes) pour chaque module présent. Un module n'édite jamais un fichier partagé.
92: - Options : `MHGP11_COORD_BITS` (18), `MHGP11_SANITIZE` (ASan + UBSan), `MHGP11_TSAN`, `MHGP11_POISON` (tampons
93:   empoisonnés), `MHGP11_MARCH` (jeu d'instructions, vide par défaut).
94: - Codes de sortie exacts (`cmake/run_expect.cmake`) : 0 conforme, 1 désaccord d'un juge, 2 refus avant calcul,
95:   3 plancher ou invariant violé, 4 mutant tué. Un arrêt par signal est toujours un échec.
96: - Toute porte porte un plancher de couverture contre le vert par vacuité.
97: - Labels CTest : `unit`, `oracle`, `diff_v10`, `scale8000`, `scale16000`, `scale32000`, `lidar`, `mutant`, `fast`
98:   (les portes `fast` n'exigent ni NumPy ni scikit-learn).
99: - Les petites tailles sont des oracles de correction ; toute conclusion de coût se mesure à 8 000, 16 000 et 32 000
100:   points et sur les trames LiDAR du contrat.
101: - Compilations et calculs hors du dépôt (`/tmp`), binaires de campagne figés depuis `git archive`.
102: 
103: ## 6. Conformité
104: 
105: La v11 calcule le même objet que la v10. La conformité se prouve par : (a) l'oracle exact borné de `reference/` ;
106: (b) des campagnes appariées contre le binaire figé de la v10 (sorties canoniques identiques octet pour octet sur les
107: mêmes entrées, trames LiDAR du contrat comprises) ; (c) des invariants globaux à l'échelle ; (d) des mutants tués.
108: Aucun benchmark ni accord moyen ne promeut un statut public.

2:

10:   permanente avant toute autre dépense.

12: - Une seule VM G4 : le développeur lance les sessions ; un auditeur demande une fenêtre par `QUESTION_AUDITEUR_*`.

51: // Reclamation saturante : si le compteur vaut begin < n, la tranche [begin, begin + min(grain, n - begin)) est prise
52: // par un seul echange compare. Le compteur ne prend que des valeurs de [0, n] et ne decroit jamais, quels que soient
53: // n et grain : aucune arithmetique ne deborde, et chaque tranche est reclamee au plus une fois (verificateur du tour 1,
54: // 29 septembre 2026 : fetch_add portait le compteur jusqu'a n + P * grain, qui repassait par 0 au-dela de 2^64, et une
55: // tranche etait executee deux fois).
56: // Echec de l'echange : une autre ecriture du compteur (reclamation ou store(n)) s'est intercalee, ou l'echange echoue a
57: // tort, ce que la forme faible permet (LL/SC ; jamais sur x86). Dans les deux cas begin est relu et le fil reessaie
58: // tant que begin < n ; il ne quitte jamais le travail sur un echec (raccord R2, mutant MV3 du verificateur du tour 2 :
59: // un « break » ici laissait, sur LL/SC, des tranches non executees ; porte pool_participation). Sans verrou mais pas
60: // sans attente : un fil peut reessayer tant que d'autres reclament ; la progression globale est garantie.
61: // Aucune exception ne sort : la premiere levee par body est conservee dans le travail, et le compteur de tranches
62: // est porte a n, si bien que toute tranche reclamee apres la capture est refusee (le compteur reste a n) ; seules
63: // les tranches deja reclamees, au plus une par fil, se terminent.
64: void Pool::run_chunks(Job& job, unsigned id) noexcept {
65:   const RegionFlag region;
66:   try {
67:     u64 begin = job.next.load(std::memory_order_relaxed);
68:     while (begin < job.n) {
69:       const u64 end = begin + std::min(job.grain, job.n - begin);
70:       if (!job.next.compare_exchange_weak(begin, end, std::memory_order_relaxed)) continue;  // begin relu, on reste
71:       (*job.body)(begin, end, id);
72:       begin = job.next.load(std::memory_order_relaxed);
73:     }
74:   } catch (...) {
75:     job.next.store(job.n, std::memory_order_relaxed);
76:     if (!job.failed.exchange(true, std::memory_order_relaxed)) job.error = std::current_exception();
77:   }
78: }
