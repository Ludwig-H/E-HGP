# Qualification locale de la branche Boost — 4 septembre 2026

Résultat : les **8 portes integer** passent avec la branche facultative Boost réellement compilée, sous C++20 Release `-O3 -DNDEBUG -Wall -Wextra -Wpedantic -Werror`. Les **16 portes lanes** passent également ; leur autorité reste OBig + littéraux, **sans usage de Boost par leur source**. Ce reçu ne remplace pas une qualification du pipeline complet et conserve `public_status=not_claimed`.

Le paquet Ubuntu officiel `libboost1.83-dev=1.83.0-2.1ubuntu3.2` (10 745 362 octets, SHA-256 dans `package.json`) a été téléchargé par APT à partir des métadonnées locales existantes, puis extrait uniquement dans `build/v7_boost_gate/extracted`. Aucun `apt update`, aucune installation système, aucun `sudo`, aucun GCP. Le header Boost système était absent avant et après. Le wrapper CMake a ajouté ce répertoire en `SYSTEM PRIVATE` aux seules deux cibles arithmétiques de son build isolé ; il ne reconstruit ni ne relie le CLI produit. Les temps présents sont des diagnostics sur hôte partagé, pas des mesures de performance.

L'autorité integer vérifiée est **Boost `cpp_int` 1.83 + OBig + littéraux indépendants** : macro `INTEGER_GATE_BOOST=1`, `BOOST_VERSION=108300`, dépendances du véritable objet compilé vers les headers privés, puis sortie d'exécution `authority=obig_literals_and_boost`. Les huit commandes et leurs codes/préfixes proviennent du CMake v7 épinglé, sans variante locale des fixtures. L'inventaire et les JUnit sont fournis, ainsi que les compteurs de non-vacuité (dont 185 Fibonacci, deux produits atteignant le mot 4 U320 et le premier bit 256). Les mutations et les rejets restent des réussites de portes à code attendu, pas des exécutions nominales du mutant.

`qualify.py.snapshot.txt` et `CMakeLists.txt.snapshot` sont des **copies textuelles inertes, octet pour octet**, des fichiers exécutés à leurs emplacements originaux sous `build/v7_boost_gate`. Ils ne doivent pas être lancés depuis ce dossier public : leurs chemins relatifs sont ceux de l'overlay original, et le runner refuse des répertoires de sortie déjà présents. Le point d'entrée du runner est `python3 -B build/v7_boost_gate/qualify.py`, depuis la racine du dépôt. Pour un rejeu, reconstituer un overlay neuf avec les mêmes emplacements relatifs, le helper de reçus et les sources épinglées, puis produire un nouveau reçu ; ne pas écraser celui-ci. Les commandes effectives et leurs bornes sont dans `summary.json`.

`LOCAL_RECEIPT_MANIFEST.json` est le manifeste original du reçu local complet, attribué à `build/v7_boost_gate/receipts` : certains fichiers qu'il référence sont volontairement omis ici. `manifest.json` est le manifeste de **cette projection publique**. `provenance.json` précise les preuves sélectionnées, les fichiers omis et leurs pins ; le dump intégral des macros et le fichier de dépendances de l'objet ne sont pas portés. Seul `integer_inventory.stdout` reçoit un LF terminal absent de l'original ; sa valeur JSON est identique. La contrelecture des JUnit vérifie les noms uniques, l'ensemble exact des 8 + 16 portes du CMake épinglé, tous les statuts `run` et l'absence de `failure`, `error` et `skipped`. Le paquet DEB, les headers extraits, les objets et les exécutables restent hors de Git ; seuls leurs hashes sont publiés. Les sources avant/après étaient identiques et le CLI protégé est resté `25c9bf8e4ef3cded5647a22f16d81af7a1e778196ad3bff73884a7f58da985f2`.
